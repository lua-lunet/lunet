The 0.19 line opens with full Windows release parity: the Windows archives
now ship every extension module the other platforms ship, and the Windows
httpc client works.

## Highlights

### Windows release parity

- The Windows archives now include everything the Unix and macOS archives
  include: `lnt_shared.lua` + `lnt_shared.dll`, `jsonic.lua` + `dkjson` +
  `lunet_jsonic.dll`, and `http_caps.lua`. lnt_shared is ported to Windows:
  its shared-memory region is backed by a page file section
  (`CreateFileMappingA`/`MapViewOfFile`), so the cdylib builds and runs on
  all three platforms with the crates' own test suites running on Windows
  in CI.
- The extension loader Lua files (`jsonic.lua`, `lnt_shared.lua`,
  `paxe.lua`, `sodium.lua`) handle Windows cdylib naming (`.dll` without
  the `lib` prefix) and split search paths containing backslashes, which
  previously made the Windows loaders silently unloadable.
- The Windows packaging is now verified, not assumed: CI checks every
  packaged archive for the required extension files and runs `lunet-run.exe`
  on a script exercising lnt_shared, jsonic, paxe, and sodium through a
  backslash `package.path`.

### httpc on Windows

- `httpc.request` no longer hangs on Windows. An extension module loaded
  from a DLL carries its own copy of libuv, so its `uv_default_loop()` was
  a second loop instance that the host's `uv_run` never polls: the request
  completed on the threadpool, but the completion callback was never
  dispatched and the Lua coroutine waited forever. The runtime now hands
  its event loop to extensions through the Lua registry, and `httpc.request`
  queues work on that loop; documented in CONTRIBUTING-INTERNALS.
- The httpc loopback smoke now also covers a plain GET before the HEAD
  case, a `file://` GET (the whole worker/curl/completion pipeline with no
  sockets), and an async `lunet.fs` read (the same threadpool machinery
  httpc rides on), so a regression in the completion dispatch is caught by
  the fs probe even if the httpc probes hang.
