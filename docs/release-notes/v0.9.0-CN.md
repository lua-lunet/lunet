- **PAXE 改为基于 paxe-core v0.1.0 的 Rust 扩展——破坏性变更。** 旧的 C 实现（`src/paxe.c`）已删除：它的线路格式从来都不是真正的 PAXE 线路格式，且文档中的开销值是错的（硬编码的 36/82；真实值是 37/97，现在在加载时从库中读取，不会再漂移）。协议核心位于独立测试的 [`paxe-core`](https://github.com/lua-lunet/paxe-core) crate——在 `ext/paxe/Cargo.toml` 中以 git tag 锁定，开发者机器上经 SSH 拉取，CI 中经令牌认证的 HTTPS 拉取——lunet 侧只提供一个薄的 C ABI 动态库（`ext/paxe`）和一个纯 Lua FFI 加载器（`lunet/paxe.lua`，与 `lunet.jsonic` 相同的加载模型）。该扩展保持纯可选：不链接进 `lunet-run`，且 libsodium 静态链接，发布归档保持自包含。
- **新的 `lunet.paxe` Lua API**：`set_local_id(node_id)` 一次性配置本节点身份；密钥按链路和 epoch 安装，使用 `keystore_set(peer, epoch, key)` / `keystore_retire` / `keystore_clear`；`seal(payload, to_id, channel)` 永远产生**标准**单接收者帧（C ABI 没有按大小选择模式）；`open(frame)` 返回明文以及经认证的 `fromId`、信道和模式，也能打开由 Rust 主机封装的可复用 DEK 扇出帧。一切帧级失败都收敛为同一条不透明的 `nil, "lunet.paxe: frame rejected"`——解释伪造帧为何失败的接收方就是解密预言机——原因只保存在 13 个累积的 `stats()` 计数器中（测量差值，绝不断言绝对值）。`paxe.protect(sock, {peer=…, channel=…})` 让单个 `lunet.udp` 套接字加入封装/打开，完全在 Lua 层接线（`src/udp.c` 未改动）；刻意不提供进程级总开关。畸形参数抛出错误；操作性失败返回 `nil, message`。
- **安全姿态**：密钥保存在 Rust 拥有的带保护页、`mlock` 锁定、释放清零的 libsodium 分配中，从不向外穿越 FFI；`paxe.init()` 要求 AES-256-GCM 硬件路径（无软件回退），默认禁用进程核心转储（`LUNET_PAXE_ALLOW_CORE_DUMPS=1` 是记录在案的调试开关），并注册 `atexit` 密钥库擦除钩子。该 crate 以 `panic = "abort"` 构建，遵守任何输入不 panic 的纪律，FFI 两侧都做验证。
- **线路格式与文档**：规范性契约是 paxe-core 的 PAXE.md；lunet 集成参考移至 `docs/PAXE.md` / `docs/PAXE-CN.md` 并已按新实现重写——正因为它现在位于 `docs/` 下，发布工作流的默认复制规则终于把它打包进了二进制归档（此前模块随包发布却没有任何可触及的协议文档，这个打包缺口已修复）。测试：`spec/paxe_spec.lua` 行为套件（随 `xmake test` 运行）、`test/smoke_paxe.lua`、双进程受保护 UDP 端到端（`test/run_paxe_udp_e2e.sh`），以及重写的 `examples/06_paxe_encryption.lua` / `examples/07_paxe_stress.lua`。
- **迁移**：与被删除的 C 模块没有线上或 API 兼容性。使用 `paxe.init`/`set_enabled`/`keystore_set(key_id, …)`/`encrypt`/`try_decrypt` 的应用必须迁移到上述 API；旧的全局开关模型由按套接字的 `paxe.protect` 取代。完整参考见 `docs/PAXE.md`。
