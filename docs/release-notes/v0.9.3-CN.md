- **新增 `lunet.sodium` 模块 —— 极简 libsodium 原语接口（SHA-256、HMAC-SHA-256、randombytes）。** PAXE 的 cdylib 已经静态链接了 libsodium，因此每个二进制发布包的使用者其实一直都在随包携带这些普通原语的字节，只是此前无法触达 —— 脚本被迫加载第二个 libsodium（Homebrew 或发行版软件包），让一个进程里出现两份 sodium，还带来 `dlsym(RTLD_DEFAULT)` 的歧义。现在恰好暴露三个函数 —— `sha256(data)`、`hmac_sha256(data, key)`（JWT HS256 原语，32 字节密钥）与 `random(n)` —— 以 `lunet_sodium_*` 符号的形式位于现有 cdylib 中。纯 Lua 加载器（`lunet/sodium.lua`，与 `lunet.paxe` / `lunet.jsonic` 同一套加载模型）通过 dylib 句柄绑定，绝不经过 `RTLD_DEFAULT`，因此同一进程里用户自带的 libsodium 永远无法截获该查找；`random` 与 PAXE 使用同一个 CSPRNG，进程永远不会混用两个随机源。该接口可独立使用（无需 PAXE 配置、没有 AES-256-GCM 硬件要求），在包括 Windows 的所有平台可用，且不触碰 PAXE 的密钥库、节点身份、计数器或失败策略。不整体导出 libsodium 命名空间：内置的 sodium 版本不是公共 ABI 承诺，整体导出也会带来符号冲突隐患。
- **文档与类型：** 新参考页 `docs/SODIUM.md` / `docs/SODIUM-CN.md` 以平实的语言写明 ABI 承诺、非目标（不提供流式变体、不提供密钥环 —— 受保护的密钥内存仍然由 `lunet.paxe` 负责）以及安全边界：无状态哈希不跨越任何秘密，而 HMAC 密钥材料确实未经保护地跨越 FFI（与 paxe 密钥库说明相同的、写明的边界姿态）。LuaCATS 注解随包发布为 `types/lunet/sodium.lua`，并与 `types/lunet/sodium.d.tl` 保持 Teal 对等；`docs/RELEASE-LAYOUT.md` / `-CN.md` 记录了发布包中的位置与独立 FFI 接口。
- **边界两侧的测试：** 已知答案向量（FIPS 180-4 的 SHA-256；用独立实现按 libsodium 固定 32 字节密钥长度重新计算的 HMAC-SHA-256 标签）既在 crate 的 Rust 套件（`xmake test-paxe`）中运行，也在新的 `spec/sodium_spec.lua` 行为套件中随 `xmake test` 运行；发布工作流对打包产物的验证现在会在每个平台上从解包后的压缩包里直接调用 `lunet.sodium` —— 与下游应用消费的完全相同的布局。
