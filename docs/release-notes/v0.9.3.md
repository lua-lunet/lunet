- **New `lunet.sodium` module — a minimal libsodium primitive surface (SHA-256, HMAC-SHA-256, randombytes).** The PAXE cdylib already statically links libsodium, so every binary-archive consumer has been carrying the bytes for these ordinary primitives inside a library they already ship — unreachable until now, which forced scripts to load a second libsodium (Homebrew, a distro package) and put two sodiums in one process with `dlsym(RTLD_DEFAULT)` ambiguity. Exactly three functions are exposed — `sha256(data)`, `hmac_sha256(data, key)` (the JWT HS256 primitive, 32-byte key) and `random(n)` — under `lunet_sodium_*` symbols in the existing cdylib. The pure-Lua loader (`lunet/sodium.lua`, same loading model as `lunet.paxe` / `lunet.jsonic`) binds through the dylib handle, never through `RTLD_DEFAULT`, so a user-owned libsodium in the same process can never capture the lookup; `random` draws from the same CSPRNG PAXE uses, so a process never mixes two RNGs. The surface works standalone (no PAXE configuration, no AES-256-GCM hardware requirement) on every platform including Windows, and touches none of PAXE's keystore, identity, counters or failure policy. No wholesale export of the libsodium namespace: the vendored sodium version is not a public ABI promise, and a full export would be a symbol-collision hazard.
- **Docs and types:** the new reference page `docs/SODIUM.md` / `docs/SODIUM-CN.md` states the ABI promise, the non-goals (no streaming variants, no keyring — guarded key memory remains `lunet.paxe`'s job) and the security boundary in plain words: stateless hashing crosses no secrets, while HMAC key material does cross the FFI unguarded (the same documented posture as the paxe keystore notes). LuaCATS annotations ship as `types/lunet/sodium.lua` with Teal parity in `types/lunet/sodium.d.tl`; `docs/RELEASE-LAYOUT.md` / `-CN.md` document the archive placement and the standalone FFI surface.
- **Tests at both sides of the boundary:** known-answer vectors (FIPS 180-4 SHA-256; HMAC-SHA-256 tags recomputed with an independent implementation against libsodium's fixed 32-byte key size) run in the crate's Rust suite (`xmake test-paxe`) and in the new `spec/sodium_spec.lua` behavioural suite under `xmake test`; the release workflow's packaged-archive verification now exercises `lunet.sodium` from the extracted tarball on every platform, the same layout downstream apps consume.
